## 〇、编号、优先级与落地规则

- 系统统一编号 `S<域>-<序号>`（域：N 网络 / G 玩法 / A 账号社交 / D 数据 / E 安全 / O 运维 / C 客户端 / T 测试）。
  一个系统一次只推进一条主线，不要在同一个提交里同时改两个契约面。
- 优先级定义：
  - **P0**：不做就无法公网、无法扩容或会丢玩家数据（等于“上线硬门槛”）。
  - **P1**：支撑可持续内容与运营（有它才像一款正式 MMO）。
  - **P2**：锦上添花，可在规模/人手允许后再做。
- **新增/修改系统的固定改造顺序（三处契约同步铁律，违反会让 `-Verify` 失败或运行时错乱）**：
  1. `shared/net/protocol.gd`：加常量 / 边界 / 数值；若是新 RPC，同时登记到 `Protocol.RPC_NAMES`；
  2. `shared/net/net_rpc.gd`：加 `@rpc` 函数 + 对外转发信号；
  3. 服务端 service（`server/scripts/*.gd`）与 `server/scripts/main.gd` 信号接线；
  4. DB 表 + **迁移**（见 S-D-1，禁止只改 `create_table` 后删库）；
  5. 客户端信号处理与 UI；6. 扩展 `client/scripts/bot.gd` 的 CHECK 断言。
- 每个系统合入前必跑：`scripts/link_shared.ps1 -Verify` → 双工程解析检查 → 起服务端 → `--bot` 自检（必要时 `--bot-check-respawn`）。

## 二、P0 系统详述（按落地顺序）

### S-D-3 + S-D-1 数据驱动与迁移（其余一切的前置）
- 现状：占位数值集中在 `shared/net/protocol.gd`；`create_table` 只在表不存在时执行，**没有迁移机制**，
  改 schema 只能手工迁移或删库（DB 在 `%APPDATA%\Godot\app_userdata\MMORPG Server\mmorpg_server.db`）。
- 做法：`Protocol` 只保留 **id 与边界**，数值搬进 `shared/` 或服务端的静态数据表（JSON/CSV，导入期校验字段与引用）；
  DB 增加 `schema_version` 表 + 顺序迁移函数，迁移在开服前执行并在失败时拒绝启动。
- 验收：干净 DB 与已有 DB 都能升级到最新版本；改数据表不改代码即可调数值。

### S-N-4 + S-N-5 兴趣管理与带宽（扩容硬门槛）
- 现状：`server/scripts/world.gd._broadcast()` 每 tick 给所有 peer 发送**全部实体**的完整状态；实体表是单个字典；
  地图 60×60 固定平面。成本是 O(实体 × peer)，单区域 10 人可用，50+ 必崩。
- 做法：按 zone/分线切分世界状态与实体表（DB 已有 `characters.zone` 列，`Protocol` 目前没有 zone 常量）；
  区域内用**均匀网格**做空间分区，按 AOI 半径筛可见实体；发送端用**优先级累加器 + 每包字节预算**决定本轮发谁，
  未被选中的实体保留累加值、下轮优先；位置量化、delta 编码按后续需要再加。
- 参考：Gaffer《State Synchronization》的 **priority accumulator / 带宽上限 / jitter buffer / quantize both sides / visual smoothing**。
- 验收：并发 50+ bot（放大量跑 `--bot`）时单 tick 广播量随 AOI 收敛；不同区域玩家互不可见；单 tick 带宽有上限。

### S-N-7 多区域 / 分线 / 实例
- 做法：定义 zone（区域）与 channel/line（分线）与 instance（副本）三层概念；`Protocol` 加 zone 常量与切换协议；
  实体 id 需在跨区域唯一（沿用保留段思路，避免与随机 peer id 冲突）；`s2c_spawn_entity` 只在进入区域时发。
- 验收：切区不重连、旧区域实体正确清理；玩家分属不同区域时互不可见。

### S-N-1 + S-N-2 预测、和解与插值（体验最大缺口）
- 现状：本地角色也完全由服务端状态驱动（`client/scripts/main.gd` 只上传输入，`client/scripts/entity_view.gd` 做插值），
  LAN 下就有约 1 个 RTT 的可见输入延迟；这是**有意取舍**，不是 bug。
- 做法（Gabriel Gambetta 系列 / Gaffer）：
  1. 把移动结算抽成 `shared/` 的**纯函数**，`server/scripts/world.gd` 与客户端共用同一套公式（避免两端各写一份而漂移）；
  2. 本地对输入立即预测并播放，输入带**序号**缓存；服务端回包带「已处理的最后输入序号」；
  3. 收到权威状态后：丢弃已确认输入 → 以权威状态为基准 → 重放未确认输入 → 平滑纠偏（误差小用指数衰减，大偏差快速收敛）；
  4. 其他实体只用**真实快照**做插值（默认显示在“过去”），为抗抖动加**抖动缓冲**，缓冲深度约 3× 发包间隔。
- 注意：这是「服务端权威 + 客户端预测」，**不等于**本文「明确不做」中的帧同步/rollback netcode。
- 验收：注入 100–200ms 人工延迟（S-T-3）时，本地输入到画面反馈 < 50ms，且与服务端位置收敛（误差 < 0.5m）。

### S-G-1 + S-G-2 技能与战斗数值
- 现状：结算集中在 `server/scripts/combat.gd`，数值是常量，单一近战。
- 做法：技能支持多冷却/多射程/多目标类型/施法时间，服务端累计 GCD 与冷却并在每次施法前校验；
  属性与伤害公式数据驱动（护甲减伤、命中/闪避、暴击、抗性），公式抽到 `shared/` 纯函数以便单测。
- 验收：bot 覆盖新技能的冷却、射程、非法目标、打断等边界断言。

### S-G-5 物品 / 装备 / 背包
- 做法：物品静态表（id、类型、稀有度、堆叠、绑定、属性修饰）；角色背包/装备为持久化实体（DB 表 + 内存镜像）；
  所有增删改由服务端裁决并落库；客户端只收“背包快照/增量”。
- 验收：物品在重登后一致；越权移动/复制物品被服务端拒绝（补 bot 负例断言）。

### S-D-2 + S-O-5 存档事务与备份
- 现状：每 10s + 断线保存，服务端崩溃最多丢 10s 进度；无备份。
- 做法：关键事件（交易、拾取、升级、掉落）立即落库；写采用事务；DB 文件定期备份并演练恢复；
  `godot-sqlite` **非线程安全**——所有 DB 访问继续只在主线程。
- 验收：kill -9 后重启，最近关键事件不丢；备份可恢复出可运行 DB。

### S-E-1 + S-E-2 传输与输入硬化（公网前置）
- 现状：凭据明文过 UDP（服务端只存哈希，**不提供传输机密性**）；限流只有账号维度，无 IP 级限制。
- 做法：登录改质询-应答（服务端 nonce + `SHA-256(salt||password)` 派生证明）或加密传输；
  限流加来源维度；所有 RPC 入参按不可信输入校验（参考 `world.gd.set_input` 对非有限值的拒绝），
  高频动作加频率上限（S-E-4）。
- 验收：抓包看不到明文口令；同来源连续错误凭据被阻断。

### S-O-1 + S-T-1 工程化与 CI
- 现状：没有单元测试框架；唯一自动化是无头 bot，只覆盖网络/玩法链路，不覆盖 UI 与纯函数。
- 做法：为 `shared/` 纯函数（边界钳制、AABB 推出、冷却/射程/伤害公式）补 GDScript 单测
  （`--script` + `extends SceneTree`）；CI 串起「`-Verify` → 双工程解析检查 → 单测 → `--bot` 自检 → 导出」；
  UI 至少维护一份人工验收清单。
- 验收：三件套能在一台干净机器上一条命令跑完并产出 Linux 服务端 + Windows 客户端。

## 三、P1 / P2 系统要点（排期时再展开）

- **S-N-3 延迟补偿**：服务端保留近 ~1s 的历史位置，命中时按“客户端看到的时间”回滚判定；只对高时效动作（远程攻击）启用。
- **S-G-3 / S-G-4 AI 与光环**：AI 用有限状态机 + 仇恨表，寻路接 Godot `NavigationServer`（注意服务端 headless 也要烘焙导航数据）；
  光环/持续效果统一为“到期/层数/驱散”三要素，避免散落在技能逻辑里。
- **S-G-8 / S-G-9 任务与经济**：任务用事件订阅（击杀/拾取/到达）驱动进度；商店价格与回收价数据驱动，货币变更走 S-D-5 审计。
- **S-G-13 / S-G-14 组队与 PvP**：先做队伍与实例，再做 PvP；实例要有明确的生命周期与弃用回收。
- **S-A-2 聊天**：使用独立 channel（可靠的聊天不应被玩法包阻塞、也不应阻塞玩法包），支持频道订阅与屏蔽。
- **S-O-3 可观测性**：至少上报 tick 耗时 P50/P99、在线数、每 tick 收发包量、DB 写入耗时；为 S-N-8 的降级策略提供依据。

## 四、技术债 / 风险（按严重度）

1. **无 schema 迁移机制**：`create_table` 只在表不存在时执行，改列只能手工迁移或删库重来（→ S-D-1）。
2. **全量广播、无 AoI**：成本 O(实体 × peer)，单区域 10 人可用，50+ 必须先做 S-N-4/S-N-5。
3. **凭据明文过线**：公网前必须处理（→ S-E-1）。
4. **限流仅账号维度**：无法阻断撞库/注册风暴（→ S-E-2）。
5. **存档非事务、崩溃丢进度**：每 10s 一次，最多丢 10s（→ S-D-2/S-D-4）。
6. **客户端无 UI 自动化**：`--bot` 不覆盖登录/角色/背包面板交互，UI 改动需人工过一遍（→ S-T-2/S-C-1）。
7. **协议无协商**：`Protocol.PROTOCOL_VERSION` 仅比对，不兼容升级会直接拒连（→ S-E-3）。
8. **仓库体积**：`server/addons/godot-sqlite/` 约 300MB 多平台二进制必须提交；按平台裁剪 `bin/` 可瘦身但会破坏其他平台导出。
9. **单点/无备份**：无备份与恢复演练，DB 损坏即全服数据丢失（→ S-O-5）。
10. **客户端预测缺失**：LAN 下就有可见输入延迟，公网体验差（→ S-N-1，属有意取舍但需补齐）。

## 五、明确不做（除非需求变化）

- 帧同步 / rollback netcode、无缝开放世界、跨服、公会战等大型系统。
- 在 MVP 阶段引入 C#、ECS 框架或自研 UDP 协议（先保持引擎原语）。
- 正式美术资产（当前全部为占位几何体：胶囊 / 方块 / 纯色）。
- 任何客户端权威的玩法判定（与本项目「服务端权威」决策冲突）。
